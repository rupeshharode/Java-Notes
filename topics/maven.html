Maven

Project object model, lifecycle phases, repositories and dependencies.

Question 1 What is Maven, and why do we use Maven in a Java project?

Maven is a build automation and dependency management tool commonly used for Java projects.

It helps us manage the project build lifecycle, including compiling, testing, packaging, verification, installation, and deployment-related tasks.

Maven provides a pom.xml file, which is used to define project information, dependencies, plugins, and build configuration.

For example, instead of manually downloading an external JAR file and adding it to our project, we declare the dependency in pom.xml. Maven automatically downloads the required dependency and its required transitive dependencies.

Maven stores downloaded dependencies in the local Maven repository, usually .m2/repository, so they can be reused by other projects.

Maven can also package our application into formats such as a JAR or WAR file.

Therefore, Maven makes dependency management and the build process easier and more consistent.

Question 2 🔥 What is pom.xml in Maven, and what information do we define inside it?

pom.xml stands for Project Object Model. It is the main configuration file of a Maven project.

It contains information about the project, such as its dependencies, plugins, version, packaging, properties, and build configuration.

The important elements include:

  • groupId — identifies the organization or group that owns the project. It is commonly based on a domain name.
  • artifactId — identifies the project or artifact.
  • version — specifies the version of the project.
  • packaging — specifies the type of artifact to be created, such as JAR or WAR.
  • dependencies — defines external libraries required by the project.
  • properties — defines reusable project properties, such as the Java version.
  • build — contains build-related configuration.
  • plugins — provides goals for tasks such as compilation, testing, and packaging. ex-the Maven Compiler Plugin compiles Java source code.

The combination of groupId, artifactId, and version is used to identify a specific Maven artifact.

Therefore, pom.xml acts as the central configuration file for a Maven project.

Q.3 Maven install

When we add a dependency to pom.xml and run mvn install, Maven first reads the pom.xml and resolves the required dependencies.

Maven checks the local repository, usually the .m2/repository directory, for the required dependency. If the dependency is not available locally, Maven downloads it from a configured remote repository and stores it in the local repository.

After resolving the dependencies, Maven executes the build lifecycle phases up to the install phase.

The main phases include:

  1. validate — validates the project structure and configuration.
  2. compile — compiles the source code.
  3. test — runs unit tests.
  4. package — packages the application, for example into a JAR or WAR.
  5. verify — performs checks to verify that the package is valid.
  6. install — installs the generated artifact into the local Maven repository.

Because Maven follows the lifecycle order, when we run mvn install, the earlier lifecycle phases are also executed.

Q.4 Maven components - compile — compiles the main Java source code into .class files and places them in the target/classes directory.

  • test — compiles and runs the project's test cases, generally located under src/test.

  • package — packages the compiled application into an artifact such as a JAR or WAR file.

  • install — installs the generated artifact into the local Maven repository, usually .m2/repository, so it can be used by other local Maven projects.

  • deploy — publishes the generated artifact to a remote Maven repository so that other developers or projects can access it.

The pom.xml essentials

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0">
    <modelVersion>4.0.0</modelVersion>

    <groupId>com.jack</groupId>       <!-- organization namespace -->
    <artifactId>order-service</artifactId>  <!-- project name -->
    <version>1.0.0</version>
    <packaging>jar</packaging>

    <properties>
        <maven.compiler.source>21</maven.compiler.source>
        <maven.compiler.target>21</maven.compiler.target>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
            <version>3.3.0</version>
            <scope>compile</scope>    <!-- compile | provided | runtime | test -->
        </dependency>
    </dependencies>
</project>

The default lifecycle phases (in order)

mvn validate     # project structure is correct
mvn compile      # src/main/java -> target/classes
mvn test         # run unit tests
mvn package      # build the jar/war into target/
mvn verify       # integration checks
mvn install      # put the jar into the local repo (~/.m2)
mvn deploy       # publish to a remote repository
# Phases run everything before them: mvn package also compiles + tests

Useful everyday commands

mvn clean                    # delete target/
mvn clean install -DskipTests
mvn dependency:tree          # see the full dependency graph
mvn test -Dtest=OrderServiceTest   # one test class
mvn spring-boot:run          # run a Spring Boot app

Scopes and dependency management

<dependencies>
    <!-- test scope: only on the test classpath -->
    <dependency>
        <groupId>junit</groupId><artifactId>junit</artifactId>
        <version>4.13.2</version><scope>test</scope>
    </dependency>

    <!-- parent POM pins versions once; children inherit -->
</dependencies>

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.mysql</groupId><artifactId>mysql-connector-j</artifactId>
            <version>8.4.0</version>   <!-- version declared here only -->
        </dependency>
    </dependencies>
</dependencyManagement>
