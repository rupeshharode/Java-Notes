Auto wiring

Autowiring in Spring means automatically resolving and injecting the dependencies required by a Spring-managed bean.

In XML-based configuration, Spring provides autowiring modes such as byName, byType, and constructor.

In byName, Spring matches the dependency with a bean whose name matches the property name.

In byType, Spring looks for a bean whose type matches the required dependency.

In constructor autowiring, Spring resolves the dependencies required by the constructor, primarily based on their types.

When using annotation-based configuration, @Autowired is commonly used for dependency injection. It primarily resolves dependencies by type. If multiple beans of the same type are available, Spring can use @Primary or @Qualifier to determine which bean should be injected.

If multiple beans match and there is no way to resolve the ambiguity, Spring throws a NoUniqueBeanDefinitionException.

Therefore, XML autowiring modes such as byName, byType, and constructor should be distinguished from annotation-based dependency injection using @Autowired.

Q.2 @Value & Spring Expression Language & @ConfigurationProperties

@Value is a Spring annotation used to inject values from property sources into fields, constructor parameters, or method parameters.

For example, if we have:

app.name=MyApplication
app.timeout=60

we can inject these values using:

@Value("${app.name}")
private String appName;

@Value("${app.timeout}")
private int timeout;

SpEl

The ${...} syntax is called a property placeholder. It tells Spring to resolve the specified property from the available property sources.

We can also provide a default value using the : syntax:

@Value("${app.timeout:30}")
private int timeout;

If app.timeout is available, Spring uses its value; otherwise, it uses 30.

@Value can also use Spring Expression Language (SpEL) with the #{...} syntax. For example:

@Value("#{2 + 3}")
private int result;

Here #{...} is a SpEL expression, while ${...} is a property placeholder.

Therefore, ${...} and #{...} should not be confused: ${...} is used for property resolution, whereas #{...} is used for Spring Expression Language.

why we use SpEL

We use Spring Expression Language, or SpEL, when we need to evaluate dynamic expressions in a Spring application.

Unlike ${...}, which is mainly used to resolve property values, SpEL uses #{...} and supports operations such as calculations, conditional expressions, method invocation, accessing objects and Spring beans, and working with collections.

For example:

@Value("#{10 > 5 ? 'Yes' : 'No'}")
private String result;

Here, SpEL evaluates the expression and assigns Yes to the field.

Therefore, ${...} is mainly used for property resolution, while #{...} is used when we need Spring Expression Language and dynamic expression evaluation.

Q.4 runner interfaces

there are two interfaces-> 1.CommandLineRunner interface 2. ApplicationRunner interface

Both have abstract method run()

They let you run custom code immediately after the Spring context is initialized but before the application starts serving requests—commonly used for tasks like seeding data, validating configs, or parsing startup arguments.

@Component public class DataSeedRunner implements CommandLineRunner { private final SeedService seedService;

public DataSeedRunner(SeedService seedService) {
    this.seedService = seedService;
}

@Override
public void run(String... args) {
    seedService.seedIfEmpty();
}

}

@Component public class EnvironmentAwareRunner implements ApplicationRunner { @Override public void run(ApplicationArguments args) { if (args.containsOption("profile")) { System.out.println("Profile: " + args.getOptionValues("profile")); } } }

@Autowired by type — and ambiguity

interface Notifier { void send(String msg); }

@Component class EmailNotifier implements Notifier { }
@Component class SmsNotifier implements Notifier { }

// Two beans of type Notifier -> constructor injection by type is now ambiguous
@Service
class AlertService {
    private final Notifier notifier;

    // org.springframework.beans.factory.NoUniqueBeanDefinitionException:
    // expected single matching bean but found 2
    AlertService(Notifier notifier) { this.notifier = notifier; }
}

Fix 1: @Primary — the default choice

@Component
@Primary                       // wins when the type alone can't decide
class EmailNotifier implements Notifier { }

Fix 2: @Qualifier — explicit pick

@Component("sms")              // bean name
class SmsNotifier implements Notifier { }

@Service
class AlertService {
    AlertService(@Qualifier("sms") Notifier notifier) {
        this.notifier = notifier;   // exactly the SMS one
    }
    private final Notifier notifier;
}

Fix 3: inject them all

@Service
class BroadcastService {
    private final List<Notifier> all;          // every Notifier bean, ordered
    private final Map<String, Notifier> byName;// key = bean name

    BroadcastService(List<Notifier> all, Map<String, Notifier> byName) {
        this.all = all;
        this.byName = byName;
    }

    void broadcast(String msg) { all.forEach(n -> n.send(msg)); }
}

Autowiring modes (know the terms)

// no        — default in plain Spring (no injection unless annotated)
// byType    — what @Autowired does first
// byName    — fallback: field/param name must match a bean name
// constructor — via @Component constructor args (best practice)

// Optional dependency with a default:
@Service
class CacheWarmer {
    CacheWarmer(@Autowired(required = false) @Qualifier("redis") Cache cache) {
        this.cache = cache;
    }
    private final Cache cache;
}
