Creation, initialization, destruction and every hook along the way.

springbeanslifecycle

Q.1 IOC, Application Context, bean lifecycle , scope, Bean Initialization ,

In Spring, the Spring IoC container is responsible for creating, configuring, and managing application objects. These objects are called Spring Beans. So, we can say that a Spring Bean is an object that is created and managed by the Spring container.

There are two common ways to define a Spring Bean: using @Component and its specialized annotations such as @Service and @Repository, or using the @Bean annotation.

@Component is a class-level annotation used to tell Spring that the class should be detected during component scanning and registered as a Spring Bean.

@Bean is a method-level annotation, generally used inside a @Configuration class. It tells Spring that the object returned by that method should be registered and managed as a Spring Bean.

For example:

@Component
public class UserService {
}

Or:

@Configuration
public class AppConfig {

    @Bean
    public UserService userService() {
        return new UserService();
    }
}

To create and manage these beans, we need to start the Spring IoC container. We can interact with the container through the ApplicationContext interface. For Java-based configuration, we can use AnnotationConfigApplicationContext and provide the configuration class:

ApplicationContext context =
    new AnnotationConfigApplicationContext(AppConfig.class);

Spring reads the configuration metadata. If the configuration class contains @ComponentScan, Spring scans the specified package for classes annotated with @Component and its specialized annotations such as @Service and @Repository. This process is called component scanning.

Before creating a bean, Spring creates a BeanDefinition, which contains metadata about how that bean should be created and configured. Based on the BeanDefinition, Spring creates the object, resolves its dependencies, injects those dependencies, and initializes the bean.

The simplified Spring Bean lifecycle can be described as:

Container startup → Read configuration metadata → Create BeanDefinitions → Instantiate bean → Inject dependencies → Apply aware callbacks and BeanPostProcessors → Initialization callbacks → Bean ready to use → Destruction callbacks → Bean destroyed

For a bean to receive a destruction callback, the Spring container needs to be properly closed, for example:

context.close();

Spring provides two major IoC container interfaces: BeanFactory and ApplicationContext. ApplicationContext extends BeanFactory and provides additional features such as event publishing, internationalization, and easier integration with Spring's other features.

The default bean scope is Singleton. In Singleton scope, Spring creates one bean instance per Spring IoC container for a particular BeanDefinition. Singleton beans are eagerly initialized by default in ApplicationContext, meaning they are normally created when the container starts.

If we need a new instance each time a bean is requested, we can use Prototype scope. In Prototype scope, Spring creates a new bean instance whenever the bean is requested from the container.

If multiple beans of the same type are available, Spring may not know which bean should be injected. We can resolve this ambiguity using @Primary or @Qualifier.

For example:

@Primary
@Component
public class UpiPayment implements Payment {
}

Or:

@Component("upiPayment")
public class UpiPayment implements Payment {
}

@Component("cardPayment")
public class CardPayment implements Payment {
}

Then we can use:

@Autowired
@Qualifier("upiPayment")
private Payment payment;

Therefore, Spring Beans are objects whose creation, configuration, dependency injection, lifecycle, and scope are managed by the Spring IoC container.

Q.4 bean scopes

Bean scope defines the lifecycle and visibility of a Spring Bean, particularly how many instances Spring creates and how long those instances are associated with the container or a particular scope.

Spring provides six commonly discussed bean scopes:

  1. Singleton
  2. Prototype
  3. Request
  4. Session
  5. Application
  6. WebSocket

1. Singleton Scope

Singleton is the default scope in Spring.

In Singleton scope, Spring creates one bean instance per BeanDefinition per IoC container.

For example, if UserService is defined as a singleton bean, Spring normally creates only one UserService instance in that container and returns the same instance whenever it is requested.

2. Prototype Scope

In Prototype scope, Spring creates a new bean instance every time the bean is requested from the container.

After Spring returns the prototype bean, Spring does not manage its complete lifecycle, particularly its destruction. When the object is no longer referenced, it can eventually become eligible for garbage collection.

Prototype scope can be useful when we need a separate bean instance for each request from the container.

3. Request Scope

Request scope is mainly used in web applications.

A new bean instance is created for each HTTP request. The same bean instance is reused within that particular request.

4. Session Scope

In Session scope, a bean instance is created for each HTTP session. The same instance can be used throughout that session.

5. Application Scope

In Application scope, a bean instance is created for the lifecycle of a web application context. It is associated with the ServletContext.

6. WebSocket Scope

In WebSocket scope, a bean instance is created for each WebSocket session/connection and is available throughout that WebSocket session.

Singleton Scope vs Singleton Design Pattern

Spring Singleton scope is not the same as the Singleton Design Pattern.

In the Singleton Design Pattern, the class itself is designed to restrict object creation so that only one instance of that class can exist within the relevant application/class-loader context.

In Spring Singleton scope, Spring maintains one bean instance per BeanDefinition per IoC container. We can still create additional objects of the same class manually using the new keyword, but those manually created objects are not the Spring singleton bean. we can use @Bean which create multipe bean defination

What happens when a Prototype Bean is injected into a Singleton Bean?

Suppose we have:

@Component
@Scope("prototype")
class PaymentService {
}

and:

@Component
class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

When Spring creates the Singleton OrderService, it resolves its dependency and injects a Prototype PaymentService instance.

However, an important point is that the same injected Prototype instance remains inside that Singleton OrderService. Spring does not automatically create a new Prototype instance every time OrderService uses that field.

If we need a new Prototype instance every time it is required, we need an appropriate mechanism such as ObjectProvider, ObjectFactory, or a lookup method.

Therefore, bean scope determines how Spring creates and manages bean instances according to their required lifecycle.

Q.5 Dependency Injection annotaion @ Autowired

@Autowired is used by Spring for Dependency Injection. It tells Spring to resolve and inject a required dependency into a constructor, field, or setter method.

When Spring encounters an @Autowired dependency, it looks for a suitable bean in the IoC container. If the required bean is available, Spring injects it. The dependency itself must be a Spring-managed bean; Spring does not simply create an arbitrary class unless that class is defined as a bean through configuration.

If multiple beans of the same type are available, Spring cannot determine which one to inject automatically. In that case, we can use @Primary or @Qualifier.

@Primary tells Spring to prefer a particular bean when multiple candidates are available.

@Qualifier explicitly specifies which bean should be injected.

For example:

@Component
@Primary
class UpiPayment implements Payment {
}

@Component("cardPayment")
class CardPayment implements Payment {
}

We can also use:

@Autowired
@Qualifier("cardPayment")
private Payment payment;

If a class has only one constructor, we generally do not need to use @Autowired on that constructor. Spring automatically uses that constructor for dependency injection.

A class can have multiple constructors because Java supports constructor overloading. If there are multiple constructors, Spring needs to know which constructor should be used for dependency injection, and we can use @Autowired to indicate the constructor.

If a required dependency cannot be resolved, Spring generally fails during bean creation and throws an exception such as UnsatisfiedDependencyException, often with a NoSuchBeanDefinitionException or NoUniqueBeanDefinitionException as the underlying cause.

If we use:

@Autowired(required = false)

Spring does not require that dependency to be available. If no suitable bean is found, Spring can skip the injection instead of failing because of that dependency.

Spring can also inject collections of beans. For example, if multiple beans implement the same interface, Spring can inject them into a List, Set, or Map.

@Autowired
private List<Payment> payments;

Here, Spring can inject all Spring-managed beans that implement the Payment interface.

Therefore, @Autowired is a mechanism that allows Spring to automatically resolve and inject dependencies from the IoC container.

The lifecycle at a glance

// 1. Container starts, reads bean definitions
// 2. Instantiation (constructor runs)
// 3. Populate properties (dependencies injected)
// 4. Aware callbacks (BeanNameAware, ApplicationContextAware...)
// 5. BeanPostProcessor#postProcessBeforeInitialization
// 6. @PostConstruct -> InitializingBean#afterPropertiesSet -> init-method
// 7. BeanPostProcessor#postProcessAfterInitialization  <-- AOP proxies are born here
// 8. Bean ready and used
// ... container shutdown ...
// 9. @PreDestroy -> DisposableBean#destroy -> destroy-method

The three initialization hooks

import jakarta.annotation.*;
import org.springframework.beans.factory.*;

@Component
class DatabaseInitializer implements InitializingBean, DisposableBean {

    @PostConstruct                          // 1st: after injection completes
    void postConstruct() { System.out.println("@PostConstruct: validate config"); }

    @Override                               // 2nd: Spring-specific callback
    public void afterPropertiesSet() { System.out.println("afterPropertiesSet"); }

    @PreDestroy                             // 1st on shutdown
    public void preDestroy() { System.out.println("@PreDestroy: flush buffers"); }

    @Override                               // 2nd on shutdown
    public void destroy() { System.out.println("DisposableBean.destroy"); }
}

init-method / destroy-method via @Bean

@Configuration
class Config {
    @Bean(initMethod = "connect", destroyMethod = "disconnect")
    public LegacyClient legacyClient() {
        return new LegacyClient();   // third-party class: no annotations needed
    }
}

class LegacyClient {
    void connect() { System.out.println("connected"); }
    void disconnect() { System.out.println("disconnected"); }
}

BeanPostProcessor — how Spring decorates beans

import org.springframework.beans.factory.config.*;
import org.springframework.stereotype.*;

@Component
class LoggingPostProcessor implements BeanPostProcessor {
    @Override
    public Object postProcessBeforeInitialization(Object bean, String name) {
        System.out.println("before init: " + name);
        return bean;
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String name) {
        System.out.println("after init: " + name);   // AOP wraps beans here
        return bean;
    }
}
