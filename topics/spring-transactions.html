Spring Transactions

@Transactional, propagation, isolation levels and rollback rules.

springtransactionsacid

1. What is a transaction, and what are ACID properties?

A transaction is a group of database operations that are treated as a single logical unit of work. Transactions help maintain data consistency and follow the ACID properties: Atomicity, Consistency, Isolation, and Durability.

  • Atomicity: All operations within a transaction either complete successfully or are rolled back if the transaction fails.
  • Consistency: A transaction moves the database from one valid state to another valid state while maintaining database constraints.
  • Isolation: Concurrent transactions are isolated from one another according to the selected isolation level.
  • Durability: Once a transaction is successfully committed, its changes remain saved even if the application crashes or shuts down.

2. What is @Transactional?

The @Transactional annotation is used to define a method or class whose operations should execute within a transaction. It is commonly used in the service layer, where multiple database operations may need to succeed or fail together.

Spring typically manages transactions through a transaction manager and AOP proxies. If a transaction fails under the applicable rollback rules, Spring can roll back the database changes.

3. What is transaction propagation?

Transaction propagation defines how a method's transaction behaves when it is called from another transactional method.

The seven propagation types are:

  • REQUIRED: Joins an existing transaction if one exists; otherwise, creates a new transaction. This is the default propagation type.
  • REQUIRES_NEW: Suspends the existing transaction, if present, and starts a new independent transaction.
  • SUPPORTS: Joins an existing transaction if one exists; otherwise, executes without a transaction.
  • MANDATORY: Requires an existing transaction. If none exists, Spring throws an exception.
  • NOT_SUPPORTED: Suspends an existing transaction, if present, and executes without a transaction.
  • NEVER: Executes without a transaction and throws an exception if an existing transaction is present.
  • NESTED: Executes within a nested transaction when supported by the transaction manager, commonly using a savepoint within the existing transaction.

4. What is transaction isolation?

Transaction isolation controls how concurrent transactions interact and helps prevent problems such as dirty reads, non-repeatable reads, and phantom reads.

The four standard isolation levels are:

  • READ_UNCOMMITTED: Allows dirty reads, non-repeatable reads, and phantom reads.
  • READ_COMMITTED: Prevents dirty reads but may allow non-repeatable reads and phantom reads.
  • REPEATABLE_READ: Prevents dirty reads and non-repeatable reads. Phantom reads may still occur, depending on the database implementation.
  • SERIALIZABLE: Provides the strongest standard isolation level and prevents these three anomalies, subject to the database's implementation.

5. What is rollback, and when does Spring roll back a transaction?

Rollback means undoing the database changes made by a transaction that has not been committed, restoring the database to its state before that transaction's changes.

By default, Spring rolls back a declarative transaction when an unchecked exception (RuntimeException) or an Error escapes the transactional method. Checked exceptions do not trigger rollback by default, but rollback rules can be customized using rollbackFor and noRollbackFor.

6. Why is @Transactional usually placed in the service layer?

The service layer contains business logic and often coordinates multiple database operations. Using @Transactional at this layer helps ensure that related operations succeed or fail as a unit.

For example, when transferring money between two bank accounts, the debit and credit operations should both succeed. If either operation fails, the transaction should roll back the changes made by that transaction.

*

Can @Transactional work on a private method?

In Spring's usual proxy-based transaction management, private methods are not intercepted as transactional entry points.

****

What happens if a checked exception occurs?

By default, Spring does not roll back for checked exceptions. You can specify @Transactional(rollbackFor = Exception.class).

**

Does @Transactional always work when one method calls another method in the same class?

Not necessarily. Self-invocation bypasses the usual Spring proxy, so the called method's transactional annotation may not be applied.

*

Does rollback undo every operation?

It rolls back transactional database changes managed by the transaction. External actions, such as sending an email, are not automatically undone.

@Transactional basics

import org.springframework.transaction.annotation.*;
import org.springframework.stereotype.Service;

@Service
public class OrderService {

    @Transactional
    public void placeOrder(Order order) {
        orderRepository.save(order);          // INSERT
        paymentService.charge(order.total()); // if this throws, the INSERT rolls back
        inventoryService.reduce(order.items());
    }   // commit happens here — all or nothing
}

Rollback rules (the interview trap)

@Service
class Rules {
    // Default: rollback on unchecked (RuntimeException, Error) ONLY.
    @Transactional
    void a() throws Exception { throw new Exception("checked"); }   // NO rollback!

    // Explicit: include checked exceptions
    @Transactional(rollbackFor = Exception.class)
    void b() throws Exception { throw new Exception("checked"); }   // rolls back

    // Or exclude a specific runtime exception
    @Transactional(noRollbackFor = IllegalStateException.class)
    void c() { throw new IllegalStateException("keep the data anyway"); }
}

Propagation — what happens when transactions meet

@Service
class Outer {
    @Transactional
    void outer() { inner.required(); inner.newOne(); inner.nested(); }
}

@Service
class Inner {
    @Transactional(propagation = Propagation.REQUIRED)      // default: join existing
    void required() { }

    @Transactional(propagation = Propagation.REQUIRES_NEW)  // suspend outer, own tx
    void newOne() { }

    @Transactional(propagation = Propagation.NESTED)        // savepoint inside outer
    void nested() { }

    @Transactional(propagation = Propagation.MANDATORY)     // fail if no tx exists
    void mandatory() { }

    @Transactional(propagation = Propagation.NEVER)         // fail if a tx exists
    void never() { }
}

Isolation levels

// READ UNCOMMITTED — dirty reads possible
// READ COMMITTED   — no dirty reads; non-repeatable reads possible (Postgres default)
// REPEATABLE READ  — stable rows; phantoms possible (MySQL InnoDB default)
// SERIALIZABLE     — full isolation, lowest throughput

@Service
class Reports {
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public Report generate() {
        // two reads of the same rows see the same data
        return reportRepository.build();
    }
}

The self-invocation trap again

@Service
class Trap {
    public void run() {
        // internal call bypasses the proxy -> NO transaction starts
        doWork();
    }

    @Transactional
    void doWork() { }
}
