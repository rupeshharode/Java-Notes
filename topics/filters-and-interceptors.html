Filters & Interceptors

Servlet filters vs Spring MVC interceptors and when to reach for each.

springfiltersinterceptors

A Filter is an interface provided by the jakarta.servlet package. It is used to process HTTP requests and responses before and after they reach the target resource.

Common use cases: - Request and response logging - Authentication and security checks - CORS handling - Request and response wrapping - Measuring request processing time

Example: import jakarta.servlet.*; import jakarta.servlet.annotation.WebFilter; import java.io.IOException;

@WebFilter("/*") public class LoggingFilter implements Filter {

@Override
public void doFilter(
        ServletRequest request,
        ServletResponse response,
        FilterChain chain)
        throws IOException, ServletException {

    long start = System.currentTimeMillis();
    System.out.println("Request received");

    chain.doFilter(request, response);

    long end = System.currentTimeMillis();
    System.out.println("Processing time: "
            + (end - start) + " ms");
}

}

Here, chain.doFilter() passes control to the next Filter or the downstream resource. When downstream processing finishes, execution returns to the Filter, allowing it to measure elapsed time.

In Spring Boot, you can register a Filter using @Component, @WebFilter with @ServletComponentScan, or a FilterRegistrationBean.

  1. What is an Interceptor in Spring MVC?

An Interceptor is a Spring MVC mechanism that intercepts requests around Controller handler execution. It implements the HandlerInterceptor interface.

It is useful for logging, handler-specific checks, and request-processing logic that depends on Controller information.

Example: import jakarta.servlet.http.*; import org.springframework.stereotype.Component; import org.springframework.web.servlet.HandlerInterceptor;

@Component public class LoggingInterceptor implements HandlerInterceptor {

@Override
public boolean preHandle(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler) {

    System.out.println("Before controller");
    return true;
}

@Override
public void postHandle(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler,
        org.springframework.web.servlet.ModelAndView modelAndView) {

    System.out.println("After handler execution");
}

@Override
public void afterCompletion(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler,
        Exception ex) {

    System.out.println("Request processing completed");
}

}

The preHandle() method returns true to continue handler processing or false to stop it.

Interview tip: A Filter runs before the DispatcherServlet processes a request, while an Interceptor runs inside Spring MVC, around handler execution.

  1. What is the execution flow of Filter and Interceptor?

  2. Client sends HTTP request

  3. Filter — before chain.doFilter()

  4. DispatcherServlet

  5. Interceptor — preHandle()

  6. Controller handler executes

  7. postHandle() and response processing

  8. afterCompletion() and Filter cleanup

  9. HTTP response returns to client

This represents a typical synchronous request. Exception handling, asynchronous requests, and response-body processing can change some callback details.

  1. What are init(), doFilter(), and destroy()?

These are the main lifecycle methods of a Servlet Filter. Method Purpose

init() Called when the Filter is initialized; used for setup.

doFilter() Executes filtering logic for a request.

destroy() Called when the Filter is taken out of service; used for cleanup. Example: @Override public void init(FilterConfig config) { System.out.println("Filter initialized"); }

@Override public void doFilter( ServletRequest request, ServletResponse response, FilterChain chain) throws IOException, ServletException {

System.out.println("Before request");
chain.doFilter(request, response);
System.out.println("After request");

}

@Override public void destroy() { System.out.println("Filter destroyed"); }

The container manages these lifecycle callbacks. They are not necessarily invoked for every HTTP request.

  1. What are preHandle(), postHandle(), and afterCompletion()?

These are the three main callback methods of HandlerInterceptor.

  • preHandle(): Called before the Controller handler executes. Returning false stops handler execution.

  • postHandle(): Called after successful handler execution and before view rendering, when applicable.

  • afterCompletion(): Called after handler request processing finishes, including applicable exception scenarios.

Example: @Override public boolean preHandle( HttpServletRequest request, HttpServletResponse response, Object handler) { System.out.println("1. Before handler"); return true; }

@Override public void postHandle( HttpServletRequest request, HttpServletResponse response, Object handler, ModelAndView modelAndView) { System.out.println("2. After handler"); }

@Override public void afterCompletion( HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) { System.out.println("3. Processing completed"); }

For a typical successful synchronous request, the callback order is preHandle() → Controller → postHandle() → afterCompletion().

  1. How do you register an Interceptor in Spring Boot?

Create a configuration class implementing WebMvcConfigurer and override addInterceptors(). @Configuration public class WebConfig implements WebMvcConfigurer {

private final LoggingInterceptor interceptor;

public WebConfig(LoggingInterceptor interceptor) {
    this.interceptor = interceptor;
}

@Override
public void addInterceptors(
        InterceptorRegistry registry) {

    registry.addInterceptor(interceptor)
            .addPathPatterns("/api/**")
            .excludePathPatterns("/api/public/**");
}

}

Here: - /api/** includes matching API paths. - /api/public/** excludes matching public API paths. The Interceptor must be a Spring-managed bean, such as one annotated with @Component, or be supplied through another valid bean configuration.

  1. Can we create multiple Filters and Interceptors?

Yes. An application can have multiple Filters and Interceptors. For Filters, use supported ordering mechanisms such as FilterRegistrationBean#setOrder() or @Order where applicable. Example: @Bean public FilterRegistrationBean loggingFilter() { FilterRegistrationBean bean = new FilterRegistrationBean<>();

bean.setFilter(new LoggingFilter());
bean.addUrlPatterns("/*");
bean.setOrder(1);

return bean;

}

For Interceptors, register them in the required order in addInterceptors(). They run in registration order during preHandle(); successful callbacks unwind in reverse order. Important: Filters and Interceptors are not chained in exactly the same way. Filters use FilterChain, whereas Spring MVC manages the Interceptor chain.

  1. What happens if preHandle() returns false?

If preHandle() returns false, Spring MVC does not execute the Controller handler, and the remaining Interceptors are not invoked normally. Example: @Override public boolean preHandle( HttpServletRequest request, HttpServletResponse response, Object handler) throws IOException {

if (!request.isUserInRole("ADMIN")) {
    response.sendError(
            HttpServletResponse.SC_FORBIDDEN);
    return false;
}

return true;

}

This example blocks requests that do not have the required role. In a real application, use the application's actual authentication and authorization design. 10. What happens if we do not call chain.doFilter()? If a Filter does not call chain.doFilter(), downstream processing does not continue through that chain invocation. For example: @Override public void doFilter( ServletRequest request, ServletResponse response, FilterChain chain) throws IOException, ServletException {

HttpServletResponse httpResponse =
        (HttpServletResponse) response;

httpResponse.sendError(
        HttpServletResponse.SC_FORBIDDEN);

}

The request is rejected before it reaches the downstream resource. Always ensure the response is handled appropriately when intentionally stopping the chain.

  1. What is GenericFilterBean?

GenericFilterBean is a Spring-provided abstract base class that adapts the Servlet Filter API to Spring's bean lifecycle and configuration facilities. It is useful when you want a Filter that integrates with Spring. public class MyGenericFilter extends GenericFilterBean {

@Override
public void doFilter(
        ServletRequest request,
        ServletResponse response,
        FilterChain chain)
        throws IOException, ServletException {

    System.out.println("GenericFilterBean executed");
    chain.doFilter(request, response);
}

}

It does not automatically guarantee that filtering happens only once per request.

  1. What is OncePerRequestFilter?

OncePerRequestFilter is an abstract Spring class that extends GenericFilterBean. It is designed to provide once-per-request filtering semantics, with behavior affected by async and error dispatch settings. It is commonly used for custom HTTP Filters, such as JWT authentication filters. @Component public class CustomFilter extends OncePerRequestFilter {

@Override
protected void doFilterInternal(
        HttpServletRequest request,
        HttpServletResponse response,
        FilterChain filterChain)
        throws ServletException, IOException {

    System.out.println("Custom filter executed");

    filterChain.doFilter(request, response);
}

}

It provides HttpServletRequest and HttpServletResponse directly, unlike the generic ServletRequest and ServletResponse parameters of Filter#doFilter().

How do you configure a Filter using @Component? In Spring Boot, a Filter declared as a Spring bean can be registered automatically in common configurations. @Component public class RequestFilter implements Filter {

        ServletRequest request,
        ServletResponse response,

For explicit control over URL patterns and order, use FilterRegistrationBean. Be careful not to register the same Filter twice unintentionally.

  1. What is the difference between @WebFilter and @Component?

  • @WebFilter is a Servlet annotation used to declare a Filter. In Spring Boot, it generally requires Servlet component scanning, such as @ServletComponentScan.

  • @Component registers the Filter as a Spring bean. Spring Boot commonly auto-registers Servlet Filter beans. Use FilterRegistrationBean when you need explicit registration settings.

  1. Can a Filter modify requests and responses?

Yes. A Filter can modify response headers and status codes, wrap requests or responses, and perform other supported operations. Example: @Override public void doFilter( ServletRequest request, ServletResponse response, FilterChain chain) throws IOException, ServletException {

HttpServletResponse httpResponse =
        (HttpServletResponse) response;

httpResponse.setHeader("X-App", "MyApplication");

chain.doFilter(request, response);

}

Reading or replacing request bodies requires care because the request input stream is normally consumable. Use an appropriate request wrapper if the body must be read and then made available downstream.

  1. Can an Interceptor modify a request or response?

Yes. An Interceptor receives HttpServletRequest and HttpServletResponse, so it can modify headers, set status codes, or stop processing. However, an Interceptor is not automatically the best choice for wrapping the request body or changing low-level Servlet behavior. Those tasks are often better handled by a Filter or a suitable wrapper.

  1. Which is better for authentication: Filter or Interceptor?

For application-wide authentication and authorization, Spring Security's filter chain is generally preferred. Reasons include: - It can enforce security before requests enter Spring MVC. - It provides established authentication and authorization mechanisms. - It supports security-context management and security-specific processing. - It can protect multiple types of resources, not only Controller handlers. Interceptors can still perform additional handler-specific checks, but they should not casually replace Spring Security.

  1. What is the difference between a Filter and Spring Security filters?

A Servlet Filter is a general Servlet API component. Spring Security uses a chain of security Filters to implement authentication, authorization, and related protections. For example, a JWT authentication Filter can validate a token and establish an authenticated security context before authorization checks take place. // Conceptual flow Request - Spring Security filter chain - Authentication - Authorization - DispatcherServlet - Controller

The exact chain depends on the Spring Security configuration.

  1. How do you measure API execution time?

A Filter can measure the total downstream request-processing time. long start = System.nanoTime();

try { chain.doFilter(request, response); } finally { long duration = System.nanoTime() - start; System.out.println("Duration in ns: " + duration); }

Using finally ensures the measurement is performed even if downstream processing throws an exception. An Interceptor can measure handler execution time using timestamps recorded in preHandle() and calculated in afterCompletion(). This measures a different portion of processing, so choose based on what you want to measure.

  1. What is the difference between addPathPatterns() and excludePathPatterns()?

Both methods configure where an Interceptor applies. registry.addInterceptor(interceptor) .addPathPatterns("/api/") .excludePathPatterns("/api/login", "/api/public/");

Here, the Interceptor applies to matching /api/** paths except the specified exclusions.

  1. Can Filters and Interceptors handle exceptions?

Yes, but their roles differ. - A Filter can catch exceptions thrown during downstream processing and handle or rethrow them. - An Interceptor's afterCompletion() receives an exception when one is propagated through the handler-processing flow. - Spring MVC exception handling, such as @ControllerAdvice, handles many Controller exceptions. Do not assume that a Servlet Filter can directly use every Spring MVC exception-handling mechanism. Filters may execute outside the MVC exception-resolution process.

  1. What is the difference between REQUEST, FORWARD, INCLUDE, ERROR, and ASYNC dispatch types?

These are Servlet dispatch types that describe how a resource is being invoked.

Type Meaning REQUEST Initial client request dispatch FORWARD Request forwarded to another resource INCLUDE Another resource included in processing ERROR Error-page processing ASYNC Asynchronous dispatch

A Filter's dispatcher types determine which dispatches it applies to. OncePerRequestFilter also provides controls for async and error dispatch behavior.

  1. Why should we avoid reading the request body repeatedly?

The request body is generally read through an input stream that is consumed as it is read. If a Filter reads it fully, the Controller may not be able to read it again. To support repeated reading, use a suitable HttpServletRequestWrapper that caches the body and exposes it to downstream processing. Be careful with large payloads and sensitive data.

Servlet Filter — runs before the DispatcherServlet

import jakarta.servlet.*;
import jakarta.servlet.annotation.WebFilter;
import java.io.IOException;

@WebFilter("/*")
public class LoggingFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request, ServletResponse response,
                         FilterChain chain) throws IOException, ServletException {
        long start = System.currentTimeMillis();
        System.out.println("Request received");
        chain.doFilter(request, response);          // next filter or the resource
        System.out.println("took " + (System.currentTimeMillis() - start) + " ms");
    }
}

Spring Boot registration options

import org.springframework.boot.web.servlet.FilterRegistrationBean;
import org.springframework.context.annotation.*;

@Configuration
public class FilterConfig {
    @Bean
    public FilterRegistrationBean<LoggingFilter> loggingFilter(LoggingFilter filter) {
        var reg = new FilterRegistrationBean<>(filter);
        reg.addUrlPatterns("/api/*");
        reg.setOrder(1);                            // chain order matters
        return reg;
    }
}

Spring MVC HandlerInterceptor — around controller execution

import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;
import jakarta.servlet.http.*;

@Component
public class TimingInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse resp,
                             Object handler) {
        req.setAttribute("start", System.currentTimeMillis());
        return true;                                // false stops the chain here
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse resp,
                                Object handler, Exception ex) {
        long ms = System.currentTimeMillis() - (long) req.getAttribute("start");
        System.out.println(req.getRequestURI() + " -> " + ms + " ms");
    }
}

import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.*;

@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new TimingInterceptor())
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/health");
    }
}
