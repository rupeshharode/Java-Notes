Atomic Classes

Lock-free thread safety with AtomicInteger, CAS and atomic references.

concurrencyatomiccas

Atomic classes (like AtomicInteger, AtomicLong, AtomicBoolean, AtomicReference) provide lock-free thread safety.

Instead of using synchronized or explicit locks, they rely on Compare-And-Swap (CAS) operations at the CPU hardware level. And avoid deadlock

CAS ensures that updates to a variable happen atomically:

The thread reads the current value.

Compares it with the expected value.

If they match, it swaps in the new value in a single CPU instruction.

If not, the operation fails, and the thread retries.

Hardware-Level Concurrency Modern CPUs have special instructions (cmpxchg on x86, in cmp add prefix lock) that implement CAS.

When two cores (say Core1 and Core2) try to update the same memory location:

Both send signals to the memory controller.

The controller ensures only one update succeeds per CPU cycle.

The "winner" core updates the value, while the other core is forced to retry.

This avoids the overhead of locking and guarantees no deadlocks.

import java.util.concurrent.atomic.AtomicInteger;

public class AtomicDemo { private AtomicInteger counter = new AtomicInteger(0);

public void increment() {
    counter.incrementAndGet(); // atomic increment
}

public int getValue() {
    return counter.get();
}

SeatBooking Problem

Scenario Thread 1 reads currentSeats = 1.

Before it can update, it gets switched to waiting state.

Thread 2 runs, sees currentSeats = 1, successfully books the seat.

availableSeats becomes 0.

Thread 1 resumes.

It still has the old value (currentSeats = 1) cached from before.

If it tries to book using that stale value, it could wrongly succeed.

✅ Why CAS (compareAndSet) prevents this CAS checks two things at the same time:

The expected value (what the thread read earlier).

The current actual value in memory.

If they match → update succeeds.

If they don’t match → update fails, and the thread must retry.

So in your example:

Thread 1 tries compareAndSet(1, 0).

But the actual value is now 0 (because Thread 2 booked).

CAS fails → Thread 1 does not book the seat.

Thread 1 retries, sees 0, and exits with “no seats left.”

AtomicInteger: lock-free counting

import java.util.concurrent.atomic.*;
import java.util.concurrent.*;

public class Counter {
    private final AtomicInteger count = new AtomicInteger();

    public void increment() {
        count.incrementAndGet();     // read-modify-write as ONE atomic op
    }

    public int get() { return count.get(); }

    public static void main(String[] args) throws Exception {
        Counter c = new Counter();
        ExecutorService pool = Executors.newFixedThreadPool(8);
        for (int i = 0; i < 1000; i++) {
            pool.submit(c::increment);
        }
        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.SECONDS);
        System.out.println(c.get());   // always 1000 — no synchronized needed
    }
}

CAS under the hood

import java.util.concurrent.atomic.AtomicInteger;

class CasDemo {
    public static void main(String[] args) {
        AtomicInteger value = new AtomicInteger(10);

        // compareAndSet(expect, update): swap only if the current value is `expect`
        boolean swapped = value.compareAndSet(10, 20);   // true — was 10
        System.out.println(swapped + " -> " + value);    // true -> 20

        // updateAndGet: retry loop built in (function may run multiple times)
        value.updateAndGet(v -> v * 2);                  // 40

        // accumulateAndGet: read-modify-write with an accumulator
        value.accumulateAndGet(10, Integer::sum);        // 50
    }
}

Other atomic types

import java.util.concurrent.atomic.*;

class More {
    private final AtomicBoolean flag = new AtomicBoolean(false);   // one-shot init
    private final AtomicLong idGen = new AtomicLong();             // unique IDs
    private final AtomicReference<String> config = new AtomicReference<>("v1");

    boolean initOnce() {
        return flag.compareAndSet(false, true);  // exactly one caller wins
    }

    long nextId() { return idGen.incrementAndGet(); }

    void updateConfig() {
        config.updateAndGet(current -> current + "-patched");
    }
}

When to use atomics vs locks

// Atomic: single variable updates — counters, flags, references.
// Lock/synchronized: multiple variables that must change together, or
//                    complex logic that cannot be one CAS operation.

class Wrong {
    private final AtomicInteger a = new AtomicInteger();
    private final AtomicInteger b = new AtomicInteger();
    // atomics are individually atomic, but updating a and b together is NOT —
    // another thread can observe a updated while b is stale.
}
