IoC & Dependency Injection

The IoC container, BeanFactory vs ApplicationContext and injection styles.

springiocdi

Q.1 What is Spring Framework? why we Use it? what is Spring container? how Spring create configure and manage objects?

Spring Framework is a Java framework used to develop enterprise and web applications. It provides many features, annotations, and built-in functionalities that reduce boilerplate code, allowing developers to focus more on business logic.

Spring provides several important features such as IoC (Inversion of Control), Dependency Injection, Spring AOP, Spring MVC, Spring Security, and transaction management. These features simplify development and make applications easier to maintain.

In a traditional Servlet-based application, developers need to manually create and manage objects, handle dependencies, and write a lot of configuration and boilerplate code. As the application grows, manually managing objects, dependencies, configurations, and other concerns becomes difficult. Spring solves these problems by providing an IoC container.

The IoC container is responsible for creating, configuring, and managing the lifecycle of application objects, which are called Spring Beans.

We commonly interact with the Spring IoC container through the ApplicationContext interface. One implementation of this interface is AnnotationConfigApplicationContext, which is used for Java-based configuration.

For example:

ApplicationContext context =
    new AnnotationConfigApplicationContext(AppConfig.class);

Here, AppConfig is a configuration class:

@Configuration
@ComponentScan("com.example")
public class AppConfig {
}

The @Configuration annotation indicates that the class contains Spring configuration, while @ComponentScan tells Spring to scan the specified package for classes annotated with @Component and its specialized annotations such as @Service and @Repository.

Spring uses this configuration metadata to identify the objects that need to be created. It then creates those objects as Spring Beans, manages their lifecycle, and injects their required dependencies.

Therefore, Spring reduces boilerplate code, promotes loose coupling through Dependency Injection, and makes large applications easier to develop, maintain, and manage.


**Interview tip:** After giving this answer, the interviewer will very likely ask **“What is IoC?”** or **“What is Dependency Injection?”** So those should be your next two concepts to master.

**Q.8** IOC, Dependency Injection ,Loose coupling ,Tight coupling , Ways To inject Dependency 

**IoC stands for Inversion of Control. It is a principle in which the responsibility of creating, configuring, and managing application objects is transferred from the application code to the Spring IoC container.**

We can interact with the Spring IoC container through the `ApplicationContext` interface.

Before using IoC and Dependency Injection, developers often created dependent objects manually using the `new` keyword. This can lead to **tight coupling**.

For example, suppose `UserService` depends on `UserRepository`:

```java
class UserService {
    private UserRepository userRepository = new UserRepository();
}

Here, UserService is tightly coupled with UserRepository because UserService is responsible for creating its dependency. If we want to replace UserRepository with another implementation, we may need to modify UserService.

With loose coupling, UserService does not create the UserRepository object itself. Instead, the dependency is provided from outside the class.

This is where Dependency Injection comes into the picture.

Dependency Injection is a technique used to provide the required dependencies to an object from an external source, such as the Spring IoC container.

Spring can identify and manage objects using configuration metadata provided through annotations such as @Component, @Service, and @Repository. These objects are managed by Spring as Spring Beans.

There are three common types of Dependency Injection:

  1. Constructor Injection
  2. Setter Injection
  3. Field Injection

In Field Injection, we use @Autowired directly on a field.

In Setter Injection, we provide the dependency through a setter method, usually using @Autowired.

In Constructor Injection, the dependency is provided through the constructor. Constructor injection is generally preferred because it supports immutability, makes dependencies explicit, and makes unit testing easier.

The dependency is provided when the object is created.

For example:

@Service
class UserService {

    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }
}

If the class has only one constructor, we generally do not need to use @Autowired on that constructor. Spring automatically uses it for dependency injection.

Therefore, IoC is the principle of transferring object-creation and management responsibility to the Spring container, while Dependency Injection is the technique through which the required dependencies are provided to objects.

  1. Constructor vs Setter Injection

Constructor injection - Dependency is provided during object creation. - Good for required dependencies. - Can use final fields. - Object cannot be created without required dependencies. Setter injection - Dependency is provided after object creation. - Useful for optional dependencies. - Dependency can potentially be changed later.

  1. Real-world IoC example

Think about a car. Without IoC, the car itself creates its engine: class Car { Engine engine = new Engine(); }

The Car is responsible for creating the Engine. With IoC, the engine is provided from outside: class Car { private Engine engine;

public Car(Engine engine) {
    this.engine = engine;
}

}

The Car doesn't control the creation of its Engine. The responsibility is transferred outside—this demonstrates Inversion of Control.

  1. Can Spring inject dependencies without annotations?

Yes. For example, with Java configuration:

@Configuration public class AppConfig {

@Bean
public UserRepository userRepository() {
    return new UserRepository();
}

@Bean
public UserService userService(UserRepository repository) {
    return new UserService(repository);
}

}

Here, we're using @Bean configuration rather than putting @Autowired on the constructor. Also, if a class has only one constructor, Spring can use that constructor automatically without @Autowired.

  1. Dependency Inversion

Dependency Inversion Principle (DIP) says that high-level classes should not directly depend on low-level concrete classes. Both should depend on abstractions.

For example: interface NotificationService { void notify(); }

class orderService { private final NotificationService noti;

public orderService(NotificationService noti) {
    this.noti= noti;
}

}

orderService depends on the NotificationService abstraction, not a specific implementation. This is one reason Spring's Dependency Injection helps us achieve loose coupling.

IoC without Spring vs with Spring

// Tight coupling: the class builds its own dependencies
class OrderService {
    private final MySqlUserRepository repo = new MySqlUserRepository(); // stuck
}

// Dependency Inversion: depend on an abstraction
interface OrderRepository { void save(Order order); }

class BetterOrderService {
    private final OrderRepository repo;
    BetterOrderService(OrderRepository repo) { this.repo = repo; }  // injected
}

// Spring = the IoC container that performs this injection for you

Declaring beans: component scan vs @Bean

@Component                      // stereotype: scanned and registered
class EmailNotifier { }

@Configuration                  // source of bean definitions
class AppConfig {
    @Bean                        // method-produced beans (third-party classes)
    public RestTemplate restTemplate() {
        return new RestTemplate();
    }

    @Bean
    public OrderService orderService(OrderRepository repo) {  // args auto-injected
        return new OrderService(repo);
    }
}

// Bootstrapping the container
ApplicationContext ctx =
        new AnnotationConfigApplicationContext(AppConfig.class);
OrderService svc = ctx.getBean(OrderService.class);

The three injection styles

// 1. Constructor injection — RECOMMENDED: immutable, testable, fails fast
@Service
class CheckoutService {
    private final PaymentGateway gateway;
    CheckoutService(PaymentGateway gateway) { this.gateway = gateway; }
}

// 2. Setter injection — for optional dependencies
@Service
class ReportService {
    private Mailer mailer;
    @Autowired(required = false)
    void setMailer(Mailer mailer) { this.mailer = mailer; }
}

// 3. Field injection — works but hides dependencies, hard to unit test
@Service
class LegacyService {
    @Autowired private Mailer mailer;
}

BeanFactory vs ApplicationContext

// BeanFactory: lazy container — creates a bean when getBean is called
BeanFactory lazy = new XmlBeanFactory(new ClassPathResource("beans.xml"));

// ApplicationContext: adds events, i18n, AOP, eager singletons.
// In Spring Boot you almost always use ApplicationContext.
@SpringBootApplication          // includes @ComponentScan + @AutoConfiguration
public class App {
    public static void main(String[] args) {
        ApplicationContext ctx = SpringApplication.run(App.class, args);
        ctx.getBean(CheckoutService.class).checkout();
    }
}
