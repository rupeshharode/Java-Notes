Servlet vs Spring Core

How the classic servlet model differs from the Spring container.

springservletcomparison

servlet vs spring core question

Q.1 Why did developers move from Servlet-based applications to Spring?

In Servlet-based applications, we often have to write a lot of boilerplate code for request handling, configuration, security, and object management. We may also need to manually create and manage objects and dependencies.

If dependencies are created manually, the application can become tightly coupled. As the application grows, managing objects, configurations, and dependencies becomes more difficult.

Spring provides many features such as the IoC container, Dependency Injection, Spring Security, transaction management, and AOP. These features reduce boilerplate code, promote loose coupling, and allow developers to focus more on business logic.

Spring does not completely replace Servlets. Instead, Spring MVC uses the Servlet API internally. For example, DispatcherServlet is a front controller that receives HTTP requests and, with the help of Spring MVC, routes them to the appropriate controller and handler method.

Q.2 If Spring provides IoC and Dependency Injection, what problem does Dependency Injection actually solve?

IoC, or Inversion of Control, is a principle in which the responsibility for creating and managing objects is transferred from the application code to a container or framework.

Dependency Injection is one way of achieving IoC. In Dependency Injection, instead of a class creating its dependency itself, the dependency is provided to the class from outside.

For example, if a UserService depends on a UserRepository, without Dependency Injection, UserService might create the UserRepository object itself. This creates tighter coupling.

With Dependency Injection, the UserRepository object is provided to UserService, for example through constructor injection, setter injection, or field injection.

In Spring, the IoC container creates and manages Spring beans and injects their required dependencies. Therefore, the developer does not need to manually create and connect all the dependent objects.

So, DI reduces tight coupling and makes the application easier to maintain, test, and modify.

Same URL, two completely different models

// Servlet: YOU create the object per request conceptually, wire it up,
//          and control the lifecycle through web.xml or @WebServlet.
@WebServlet("/users")
public class UserServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws java.io.IOException {
        // manual wiring: build dependencies yourself
        UserRepository repo = new JdbcUserRepository();   // hardcoded!
        UserService service = new UserService(repo);      // new, new, new
        resp.getWriter().println(service.all());
    }
}

// Spring Core: the IoC container creates and wires the objects for you.
@RestController
@RequestMapping("/users")
public class UserController {
    private final UserService service;      // injected — no `new` anywhere

    public UserController(UserService service) {   // constructor injection
        this.service = service;
    }

    @GetMapping
    public List<User> all() { return service.all(); }
}

The core differences in one table

// | Aspect          | Servlet API                 | Spring Core                     |
// |-----------------|-----------------------------|---------------------------------|
// | Who creates objs| container creates servlets  | IoC container creates beans     |
// | Wiring          | manual (new + web.xml)      | automatic (@Autowired/@Bean)    |
// | Lifecycle hooks | init/service/destroy        | @PostConstruct/@PreDestroy etc. |
// | Config          | web.xml / annotations       | @Configuration / application.yml|
// | Testability     | hard — dependencies new-ed  | easy — swap bean implementations|
// | Scope           | one servlet class per URL   | any class can be a bean         |

// Spring MVC still runs ON TOP of the servlet API:
// DispatcherServlet IS a servlet — Spring manages it for you.
